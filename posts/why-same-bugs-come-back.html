Why AI-built systems keep getting the same bugs, and why tests didn't catch them

Yu Han Tey · 19 October 2026 · 5 min read

For a while I was vibe coding: AI wrote the code, and I trusted it fully without checking much myself.

In five weeks I fixed 103 bugs. 70 of them were repeats: the same root cause, back in a new form. Every repeat meant another pull request.

Short answer

Only about 1 in 7 repeats was a badly worded prompt. The rest came from five habits, like patching the symptom or testing a fix only on its own bug.

Tests didn't catch them because tests checked something easier than real use.

01How I sorted them

I went back through every bug and sorted it by its root cause, not by where it showed up. "The page said updating forever" is where. "Two timestamps came from two different clocks" is the cause.

Then I kept only the bugs that came back in a new form. That left 70.

Only about 1 in 7 repeats was a badly worded prompt.

Most came from not thinking a case through.

Other developers describe the same loop, and it shows up across many popular coding tools. In one team, a bug had been "fixed" three times, each time with green tests, while the real cause stayed untouched. The agent was right that the symptom would go away. It was wrong about why.

02The five habits behind the repeats

  1. I patched the symptom, not the causeOne problem took 11 pull requests before I found the real cause: a single setting.
  2. A fix was tested only on its own bugSo it broke something next to it, and that became the next bug.
  3. I fixed one path and missed the othersThe same data could come in through a second door I hadn't checked.
  4. Tests didn't take the path real use takesSo a fix passed its test while the bug was still there.
  5. Failures were silentProblems showed up late and one at a time, so each one became its own fix.

03Why the tests and evals didn't catch them

Every one of these fixes had a passing test. The tests weren't wrong. They checked something easier than real use.

What the test checked                  Where the bug was
─────────────────────────────────      ─────────────────────────────
the case I just fixed             ✓    the case next to it            ✗
a fake model                      ✓    the real model's API           ✗
parts connected by hand in test   ✓    parts connected by the real app ✗
5 similar examples                ✓    13 in real data                ✗

Only the case I fixed

A new rule removed an old preference when a new one contradicted it. Its tests were all about real contradictions, so they passed. Nobody wrote a test for two preferences that only look alike. That was exactly the case that broke.

A fake model instead of the real one

To keep tests fast, the model was replaced with a fake that returned a fixed answer. The fake accepted an output format that the real model's API rejected. Every test passed; every real call failed.

A test path that production doesn't take

My eval sent requests one way, and production sent them another. In production, the model skipped an optional field it never skipped in the eval. In another case, the test connected two parts by hand, in the right order. The real app connects them its own way. If the app's order ever changed, the test would still pass, because it never used the app's version.

Test data smaller than real data

The biggest group of similar items in my test cases had 5. Real data had 13. A check that worked on 5 broke on 13.

A passing test proves the test passed. It only proves the feature works if the test looks like real use.

04How I stop the repeats

I patched the symptom
→
Find the cause firstIf the same thing needs a second fix, I stop asking AI for another patch. It finds the root cause and shows me the evidence.
Tested a fix only on its own bug
→
Test the neighboursA rule that removes things also gets cases that look similar but must stay.
Fixed one path, missed the others
→
List every path firstEvery place the data can get in, not just the one that broke.
Tests didn't follow real use
→
Test the way it really runsThe real model, the production path, data as big as real data. End-to-end in a real browser, with screenshots.
Failures were silent
→
Make every failure loudMarked as an error, with the reason. All errors at once.

And one rule over all of them: every old bug becomes a test, and every change runs the whole set.

These fixes became part of how I work with AI now. The full loop is in How I build with AI: a 9-step loop.

05Where I could be wrong

  1. "Prompt" or "thinking" is my callSome fixes changed what the model is given, not how the prompt is worded. Count those as prompt problems, and prompts become about 1 in 3 repeats. Still not the biggest group.
  2. Sorted by one personI sorted the bugs myself, from my own notes. Someone else might group them differently.

06FAQ

Why do systems built with AI keep getting the same bugs?

In my case, most repeat bugs were not badly worded prompts. Only about 1 in 7 was. The rest came from patching symptoms instead of causes, testing a fix only on its own bug, missing a second path for the same data, tests that don't follow real use, and failures that stay silent.

Why don't unit tests and evals catch AI-written bugs?

Because they test something easier than real use: only the case that was fixed, a fake model instead of the real API, parts connected by hand only in the test, or a few small examples when real data is bigger. The bug lives in the gap between what the test checks and what production does.
